# 下一版先解决什么

这是一份基于 0905v1 当前实现的讨论草案。以下排序是开发侧建议，尚未经过用户访谈验证，也不代表开发排期或已经具备的功能。

## 一个账号和多个账号，最先需要的东西不同

只有一个账号的人，可以用 Next 看额度，也能自动暖号。官方额度、重置时间、已有用量统计、会员日期和单账号专注界面都适合这个场景。开启暖号后，Next 会在窗口结束且检查通过时发送最小请求，尝试启动下一窗口，省掉用户手动发一句话的操作。暖号仍需 Hub 映射与空闲检查，5 小时暖号还受参与调度开关控制；选择 CLI 模型还要建立独立环境。这些条件使首次使用比界面看上去复杂。详细规则见 [5 小时窗口说明](../../README.md#五小时窗口与自动暖号的关系)。

管理多个账号的人，更需要分清每个账号的额度、环境、任务状态与执行偏好。Next 已提供隔离 CLI、每账号模型设置、批量应用和 Hub 状态提示，但状态检查与实际启动之间仍有时间差。低额度候选也只是提示，不是经过全部执行检查的自动派单。

两类人可以共用同一应用。首页先展示当前场景需要的信息，再提供高级功能，比另做两套产品更容易保持功能一致。代价是界面必须准确说明当前模式和依赖条件，不能让灰色按钮成为首次使用的终点。

## 建议优先讨论的四项

| 建议顺序 | 当前问题 | 候选改进，尚未实现 | 需要接受的代价 | 最小验收方式 |
| --- | --- | --- | --- | --- |
| 先做 | 单账号用户要自动暖号或启动 CLI，也要理解外部 Hub 和手动映射 | 增加引导，把看额度、自动暖号、本机任务和 Hub 协作的条件讲清；评估本机模式使用跨进程占用锁 | 本机锁无法协调不遵守协议的外部入口，不能只移除 Hub 检查就放行；仍不得静默改写系统登录 | 不编辑 JSON 完成引导；暖号与任务同时申请时只有一方成功；无法确认占用时停止启动并解释原因 |
| 同等重要 | 多入口同时通过快照检查，仍可能重复使用同一账号 | Next 与外部调度器共用原子占用申请、存活确认与释放协议 | 所有入口必须配合升级，不能仅修改 UI 或按超时无条件解锁 | 两个入口同时请求同一账号只能有一个获准；运行中不能被回收；异常退出后有可验证的恢复路径 |
| 接着做 | 失败信息、Hub 配置错误、历史失败和当前状态容易混在一起 | 在原账号卡补充状态原因、证据更新时间与可执行的下一步；过往失败放入记录 | 解释需要准确分类，不能把网络故障当成登录失效；不得输出密钥或任务正文 | 用户能分清需要登录、需要配置、额度不足和网络问题；不再用旧失败描述新窗口 |
| 看反馈 | 多账号列表较长，用户寻找当前可用账号需要逐项看 | 在现有列表增加忙碌、空闲、低额度筛选和一个简洁任务摘要 | 摘要可能泄露工作信息；默认只展示账号备注、状态、来源和时间，不显示任务正文 | 账号较多时能快速找到目标；状态未知不会被归为可用；新筛选不改变原排序和调度资格 |

本机模式和跨入口占用协议需要共同设计。先把本机按钮放开、以后再补全协调，会使现在保留的保护失效。

## 暂时不急着增加的东西

更复杂的动效、新的独立页面和大量统计卡片可以先放后面。单账号首次启动和多账号重复占用还没有处理好时，这些变化很难减少用户的实际操作。

任务模板、额度恢复提醒和通知摘要值得继续讨论，但不把它们直接列为下一版承诺。自动暖号已经存在，待讨论的是是否需要限制在工作时段、设每日维护请求上限，以及把现有的请求发送与窗口确认提示保留成更清楚的记录。需要先知道用户的工作时间、是否反复执行同类任务，以及愿意接收多频繁的提醒。

## 希望用户带回来的信息

请到现有 [Issues](https://github.com/BLACKIELF/codex-account-manager-next/issues) 留言。不要上传真实邮箱、凭据、Webhook、完整配置、任务正文或未经脱敏的日志和截图。

可以直接复制下面几行填写。

```text
我的账号数量是 1 个 / 2 至 3 个 / 4 个以上
我主要使用 Codex App / CLI / Hub 协作
我最常重复的一步是
最近一次这一步让我卡住的情况是
如果只能先改一项，我希望是
改完后，我会通过这个结果判断它有没有用
```

最想讨论的问题是，如果下一版只能帮你少做一步，你希望省掉哪一步？
